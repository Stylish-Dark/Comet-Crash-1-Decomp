# SPU-prepared submesh batching path

The previously opaque tail of each 0x78-byte submesh record is now structurally
recovered from the exact NPEB00142 v1.00 executable and the original shipped
`*_spu.vpo` shaders.

This is a **legacy PS3 batching path**, not an architecture the native port is
required to reproduce. The recovered semantics are useful because the native
renderer can replace the expanded SPU streams with normal GPU instancing while
preserving draw behavior.

## Legacy submesh fields

| submesh offset | recovered meaning |
| ---: | --- |
| `+0x64` | byte-sized batch/SPU-path enable gate, set when the `+0x5C` `_spu.vpo` program loads |
| `+0x68` | per-frame batched instance count |
| `+0x6C` | generated batched vertex-stream pointer |
| `+0x70` | generated batched u32 index-stream pointer |
| `+0x74` | generated per-instance `objInfo` vec4 stream pointer |

`+0x64` is persistent material/program capability state rather than a
per-frame counter. Program helper `0x00101960` reads material `+0x4C`
(submesh `+0x5C`) and stores its non-null result as this byte at
`0x00101F20`.

Fields `+0x68..+0x74` are transient per frame. The coordinator later resets
`+0x68` to zero after the batched work has been consumed.

## Batch preparation: PPU `0x000FEFB0`

Function `0x000FEFB0` loops the model's 0x78-byte submeshes.

The key control flow is:

```text
0x000FF060  read byte submesh+0x64
0x000FF068  clear submesh+0x68
...
0x000FF12C  store selected batch count -> submesh+0x68
0x000FF134  use/update submesh+0x6C vertex stream
0x000FF138  use/update submesh+0x70 index stream
0x000FF13C  use/update submesh+0x74 object-info stream
```

The selected batch count is clamped by the requested object range and available
output-buffer capacity before helper/job `0x00138248` is scheduled.

The pointer advances after that job prove the exact generated byte counts:

```text
vertex bytes = batch_count * model_vertex_count * 32
index bytes  = batch_count * submesh_index_count * 4
objInfo bytes = batch_count * 16
```

The 32-byte vertex product is formed around
`0x000FF2A0..0x000FF2D0`.

## Renderer: PPU `0x00100750`

When `submesh+0x68 != 0`, the renderer enters the batched path.

The generated vertex stream at `+0x6C` is bound with a 32-byte stride:

```text
+0x00  vec4 primary vertex input
+0x10  vec4 Cg parameter "normal_ty"
stride 0x20
```

The `objInfo` Cg parameter is sourced from `submesh+0x74` as a vec4 stream
with a 16-byte record per batched instance.

The indexed draw at `0x001009E8` uses:

```text
mode       = GL_TRIANGLES
start      = 0
end        = batched_instance_count * model_vertex_count - 1
count      = batched_instance_count * submesh_index_count
index type = GL_UNSIGNED_INT (0x1405)
indices    = submesh+0x70
```

This differs intentionally from the ordinary model path, which uses the
model's static u16 index buffer.

After the batched draw the visible-object/range cursor advances by
`submesh+0x68`, proving that this field counts model instances consumed by the
batch rather than vertices or indices.

## Original shader evidence

The original game data contains `*_spu.vpo` variants including:

- `lit_object_shader_spu.vpo`
- `lit_texture_shader_spu.vpo`
- `lit_texture_spec_shader_spu.vpo`
- `lit_texture_spec_gloss_shader_spu.vpo`

Their embedded Cg parameter metadata includes:

```text
position_tx  POSITION
normal_ty    TEXCOORD0
objInfo      TEXCOORD1
```

The renderer itself looks up `normal_ty` around `0x00100810` and
`objInfo` around `0x001008E8`, tying those shipped shader inputs directly to
the recovered 32-byte expanded vertex stream and 16-byte per-instance stream.

## Native boundary

The native representation is in
`decomp/include/comet/model_batching.hpp`.

It records the proven legacy offsets and exact stream-size/draw-count formulas.
It does **not** emulate SPU jobs. A native renderer should normally express the
same behavior as an instance list plus static model geometry, generating or
expanding vertices only where a recovered gameplay/rendering dependency proves
that necessary.
